# Owned range executor

October 13, 2026: the owned-range GPU acceptance passed three qualification checks and one 1,048,576-candidate #71 assignment. Its Pod was deleted after 79 seconds. The native binary is qualified for that bounded run; sustained throughput and exhaustive coverage remain unverified. Existing benchmark approvals cannot authorize range work.

The executor maintains the authoritative live owned-range ledger in the same private SQLite database as run state. `RangeBridge` retains the configured job as a migration seed. New owner-triggered range drafts select an eligible unfinished job with the same solver before reserving a fresh disjoint range of the configured assignment size. Reservations, checkpoints and completed history survive service restarts. Repeated drafts reuse the same unstarted reservation. Local staging plans are preparation records; live accepted checkpoints come from this server. External reports are never used for range allocation or completion credit.

The operator can obtain `quote-range-ai` with `{limits:{maxDurationSeconds,capMicrousd}}` through the existing private owner socket. The server selects the job automatically; optional `jobId` requests an existing eligible assignment explicitly. The quote and bounded options include the immutable mission and `resumeFrom` checkpoint. A recorded model choice selects one supplied option or holds. `propose-ai` persists it without approving or renting. A pending submission retries the saved ticket and choice, including its allocated job, without another reservation or model request. The direct private `propose-range` action also accepts an omitted job ID for automatic selection. These owner commands remain private and require exact Google owner approval before dispatch.

`resumeFrom` is included in the signed run terms. Remaining candidate counts and archived run credit exclude the completed prefix. Approval, proposal persistence and the final pre-create transaction recheck the checkpoint and job state. A stale proposal cannot rent a GPU for completed or changed work. Active rentals block replacement drafts; an unfinished lease must expire before reassignment, even after its old Pod is deleted. A replacement lease increments the epoch and fences old worker keys, capabilities and receipts. Private-review targets stay paused. Legacy saved missions without `resumeFrom` are readable and cannot authorize a changed checkpoint.

Configuration binds the migration seed and assignment size, native solver checksum, worker archive/build/bootstrap/image, chunk size and recovery public-key fingerprint. Every proposed job's identity, bounds and checkpoint bind independently to that immutable ledger row. Changed deployment artifacts or mission bindings require reapproval before creation. The run uses the existing single-rental limit, fresh capacity/price checks, ambiguous-create reconciliation and independent shutdown/deletion controller. Allocation never authorizes recurring rentals.

Enrollment binds the Pod and Ed25519 worker key before returning the range configuration. A domain-separated capability derived from the private bootstrap token can be reconstructed after a response loss; retries preserve the exact job/epoch/key/expiry. It grants only two task/receipt routes. The default ledger rejects production enrollment without the trusted approval adapter. No worker receives provider credentials, owner recovery private material, Google session data or owner-socket access.

The public HTTPS proxy exposes only POST `/worker/range/task` and `/worker/range/receipt`; loopback Node handlers trust this fixed deployment boundary, not a forwarded header. Nginx retains strict method/query/body/rate limits. Worker clients validate TLS, have bounded responses and follow no redirects. The read-only dashboard proxy forwards no visitor authorization and cannot invoke owner controls or worker enrollment.

GPU startup verifies the complete pinned runtime manifest and hardware model claim, then the three native known-answer cases before fetching a #71 chunk. Positive, exclusive-end negative and cross-batch/tail checks stay separate from owned coverage. A signed range archive is accepted only when all three cases validate and the server ledger independently agrees with the worker's completed/private-review state. A passed completion requires that archive; failed completion and rental deadlines still lead to shutdown.

Apparent #71 candidates are verified and sealed to the approval-bound RSA-3072/OAEP-SHA256 public key before receipt transmission. Encrypted candidate evidence remains private, the target pauses and that chunk receives no coverage. The configured owner's private recovery key was generated on the desktop, protected with Windows DPAPI CurrentUser and roundtrip-checked; it was not uploaded. Recovery/backup must preserve that desktop material. No candidate was discovered during preparation.

Validation before GPU acceptance: 212 backend/executor tests and 57 hosted dashboard tests passed; 24 executor tests passed on the deployed Linux host. HTTPS worker artifact digest and unauthenticated-task rejection were read back. The native binary passed 16 inspect-only checks, which perform no GPU work. Signatures and counts remain authenticated worker claims, not independent hardware or exhaustive-search attestation. Final provider billing is a separate reconciliation step.

The existing host retains pre-deployment configuration/source/database snapshots privately. Restricted SSH, off-host backup retention, multi-GPU scheduling, treasury funding and physical/exhaustive-search attestation remain future work. Publication/deployment of code does not start a rental; owner approval is still required.
